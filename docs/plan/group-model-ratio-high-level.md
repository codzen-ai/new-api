# 分组模型倍率（GroupModelRatio）— 高层方案

> 目标读者：决策者 / 需要快速判断可行性与投入的人
> 配套文档：`group-model-ratio-detailed.md`（逐文件、逐函数的详细实现）

## 1. 要解决的问题

当前 new-api 的计费公式是：

```
额度 = 模型倍率(全局按模型名) × 分组倍率(全局按分组名) × token 数 × 补全倍率
```

其中**分组倍率是整组一个标量**，对该分组下的所有模型一视同仁。

这导致一个转售场景无法实现：

> 「给 VIP 客户便宜卖 GPT 系列，但 Claude 系列不打折。」

因为把 VIP 分组倍率调到 0.8，会同时把 GPT 和 Claude 都打折，无法只折其中一部分模型。系统里不存在「分组 × 模型」维度的价格覆盖。这也是官方已知缺口（见仓库 Issue #4602）。

## 2. 目标

### 2.0 需求对齐（三条，全部纳入 Phase 1）

| # | 需求 | 方案落点 | 状态 |
|---|------|---------|------|
| 1 | 管理员可在**前端**为不同用户组设置模型倍率 | 后台二维编辑器（分组 → 模型 → 倍率） | Phase 1 |
| 2 | 有分组模型倍率的**优先使用**分组模型倍率 | 计价时命中即替换全局模型倍率，未配置回退 | Phase 1 |
| 3 | 用户能**看到当前分组的模型价格** | 定价接口按分组返回生效倍率 + 定价页按分组展示 | Phase 1 |

> 第 3 条需要改造定价接口与前端定价页的价格计算（当前是「一模型一倍率 × 分组标量」，需升级为「按分组取生效模型倍率」）。详见详细方案 §4。

### 2.1 机制

新增一张可选的 **分组 × 模型倍率覆盖表** `GroupModelRatio`：

- 结构：`{ 分组名: { 模型名: 倍率 } }`
- 命中时，该倍率即为这个分组下这个模型的**最终倍率**，**分组倍率对它失效**（覆盖即最终价，需求方已确认）；未配置则回退到现有 `全局倍率 × 分组倍率`。
- 补全倍率等其余机制不变（仍按覆盖后的模型倍率比例作用于输出）。

配置示例（VIP 只折 GPT，Claude 不动）：

```jsonc
GroupModelRatio = {
  "vip": {
    "gpt-4o":      5,    // VIP 的 gpt-4o 最终倍率就是 5（全局是 10）
    "gpt-4o-mini": 0.3
  }
  // 未列出的模型（如 claude-3-5-sonnet）→ 回退 全局倍率 × 分组倍率
}
GroupRatio = { "vip": 0.9 }   // 该组全局折扣 0.9：只作用于「未覆盖」的模型
```

效果：VIP 客户仍调用标准模型名 `gpt-4o` / `claude-3-5-sonnet`，无需改名、无需重定向渠道。`gpt-4o` 按专价 5（不再受 0.9 影响），`claude-3-5-sonnet` 按 `全局 × 0.9`——**同组内可精确区分"按专价的模型"与"走全局折扣的模型"**。

## 3. 使用指引（管理员操作手册）

> 本节面向功能上线后**使用该功能的站点管理员**，说明它是什么、怎么用。

### 3.1 功能介绍

**分组模型倍率**让你为**不同用户组**的**特定模型**单独定价，而不必对整个组统一打折。

- **原来**：分组倍率是"一刀切"——把 VIP 组设为 0.8，则该组**所有**模型（GPT、Claude…）一起打折，无法只优惠一部分。
- **现在**：你可以精确指定"VIP 组的 `gpt-4o` 按倍率 5"，而该组其它未单独设置的模型（如 `claude-3-5-sonnet`）照旧走全局价 × 分组倍率。

**核心规则（务必理解）：覆盖即最终价。**
一旦你为某个 (分组, 模型) 设置了倍率，这个数字就是该组该模型的**最终倍率**，该组的分组倍率对它**不再生效**（不会再叠加打折）。没有单独设置的模型，仍按"全局倍率 × 分组倍率"计算。

**适用范围**：仅对**按量计费（按 token 倍率）**的模型生效。按次固定价模型、表达式计费模型暂不支持（会"设了不生效"），后台会作相应提示。

**典型场景**：转售时给不同客户分组卖不同价——例如 VIP 客户 GPT 系列优惠、Claude 系列原价；或给某个大客户的专属分组单独定一套模型价。

### 3.2 操作流程

**第 1 步：准备分组**
确认你已有对应的用户分组（如 `default` / `vip` / `client_acme`），并已把目标客户的用户或令牌划入该分组。（分组本身的创建/可见性在"分组倍率设置"与"可用分组"中管理。）

**第 2 步：确认模型已对该分组开放**
确保目标模型有渠道服务该分组（即该模型在这个分组下可用）。否则倍率设了也用不上、定价页也不会显示。

**第 3 步：进入配置页**
后台 **系统设置 → 分组与模型定价设置 → 分组模型倍率**。

**第 4 步：添加分组模型倍率**
1. 选择要配置的**分组**（如 `vip`）。
2. 添加一行：选择**模型**（如 `gpt-4o`）+ 填写**倍率**（如 `5`）。
3. 需要多少模型就加多少行；需要几个分组就切换分组分别配置。
4. **保存**。配置即时生效（无需重启）。

**第 5 步：验证**
- 用该分组下的账号/令牌登录，打开**定价页**，切换到该分组，确认目标模型显示为你设置的价格、其它模型不受影响。
- 或用该分组的 key 实调一次，核对账单扣费与预期一致。

### 3.3 一个完整例子

目标：VIP 组的 GPT 便宜，Claude 保持原价，同时 VIP 组其它模型享 9 折。

| 配置项 | 值 | 效果 |
|--------|----|----|
| 分组倍率 `vip` | `0.9` | VIP 组"未单独定价"的模型统一 9 折 |
| 分组模型倍率 `vip → gpt-4o` | `5` | VIP 的 `gpt-4o` **最终就是 5**（不再乘 0.9） |
| 分组模型倍率 `vip → gpt-4o-mini` | `0.3` | 同上，最终 0.3 |
| （`claude-3-5-sonnet` 不设置） | — | 走 `全局倍率 × 0.9` |

VIP 客户照常调用标准模型名 `gpt-4o` / `claude-3-5-sonnet`，无需改名。

### 3.4 注意事项（避免踩坑）

- **覆盖即最终价**：设了 (vip, gpt-4o)=5，就是 5，不会再叠该组的分组倍率。想让某模型"在全局折扣基础上再微调"时，请自己把这层折扣算进你填的数字里。
- **只对按量模型生效**：给固定价 / 表达式计费模型设倍率不会生效。
- **模型要先对该分组开放**：没有渠道服务该分组的模型，设了也是死配置，定价页也不显示。
- **价格可见性**：某分组的模型价，只有该分组的用户能在定价页看到；匿名访客与其它分组用户看不到（专属/私有分组价格不外泄）。
- **一客户一分组**：本功能按"使用分组"定价，请保证客户稳定归属一个分组。

## 4. 实现思路（为什么改动可控）

关键在于：**实际结算复用预扣阶段算出的 `PriceData`（含 `ModelRatio` 与 `GroupRatioInfo.GroupRatio`）**（已在代码中确认，`service/quota.go` 结算读的是 `relayInfo.PriceData.*`）。

因此只要在**计价入口** `relay/helper/price.go` 的 `ModelPriceHelper` 里，命中覆盖时把 `modelRatio` 设为覆盖值、同时把 `groupRatio` 归一为 1.0（覆盖即最终价），**预扣和最终结算就自动一致**，无需改动结算主逻辑。为避免"覆盖 modelRatio 与归一 groupRatio"两步在多个计费点漏做，封装为单一解析器 `ResolveGroupModelPrice`（详见详细方案 §3.5）。

改动是「照抄现有 `GroupGroupRatio` 机制、再多加一层查找」的模式：

| 层 | 改动 | 参照现成代码 |
|----|------|------------|
| 配置存储 | 新增 `GroupModelRatio` 配置项 + 读写/校验函数 | 完全仿照 `GroupGroupRatio`（同文件） |
| 后台接入 | `model/option.go` 加 2 行（展示 + 更新路由） | 仿照 `GroupGroupRatio` |
| 计价注入 | `ModelPriceHelper` 主注入 1 处 + 实时(WSS)旁路 1 处 | — |
| 定价展示 | `controller/pricing.go` 按分组显示时套用覆盖 | 已有按分组算价逻辑 |
| 前端配置页 | 新增二维编辑器 | 照抄 `group-ratio-visual-editor.tsx` |
| 测试 | 表驱动单测：覆盖命中/回退/0 价/与分组倍率组合 | 仿 `service/text_quota_test.go` |

**无需数据库迁移**：配置沿用现有 options 表的 JSON 存储机制，天然三库（SQLite/MySQL/PostgreSQL）兼容。

## 5. 范围与分期

**Phase 1（本方案核心，覆盖绝大多数转售需求 + 上述三条需求）**
- 分组 × 模型的**模型倍率**覆盖（输入价；输出价通过补全倍率按比例联动）— 需求 2
- 后台**前端二维编辑器**（管理员按分组设模型倍率）— 需求 1
- **定价页按分组展示**：定价接口按分组返回生效倍率，前端定价页显示当前分组的模型价 — 需求 3
- 单测

**Phase 2（可选增强，按需再做）**
- 分组 × 模型的**补全倍率**独立覆盖（输入输出价可解耦）
- 分组 × 模型的**固定价**（按次计费模型，如绘图/任务类）覆盖
- 分组 × 模型的缓存/音频/图片倍率覆盖

## 6. 风险与注意点

- **auto 分组**：覆盖读取发生在分组解析（`HandleGroupRatio`）之后，用的是最终生效分组，行为正确。
- **覆盖即最终价**：命中覆盖时必须把 `groupRatio` 归一为 1.0（含清除特殊分组倍率），否则会与分组倍率叠乘；封装 `ResolveGroupModelPrice` 统一处理，杜绝漏归一。
- **免费模型判定**：若覆盖倍率设为 0，现有「倍率为 0 即免费」逻辑自动生效，无需特判。
- **实时(WSS)/音频旁路**：`PreWssConsumeQuota` 会独立重取倍率，需同步注入覆盖（详见详细方案），否则实时类模型计费会漏掉覆盖。
- **缓存一致性**：配置更新走现有 `config.GlobalConfig` 热更新，与 `GroupGroupRatio` 同路径，无额外缓存问题。
