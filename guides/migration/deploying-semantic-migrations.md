# 语义迁移的部署窗口问题（蓝绿 / 滚动部署）

面向执行升级的人或自动化助手。这份文档说明一类**与具体功能无关**的部署风险：
当一次升级会改变数据库里某个值的**含义**（而不是只加字段、只改代码），
新旧两个版本在部署期间同时在跑的那几分钟里，旧版本会按旧含义解释已经被改写的数据。

已知的语义迁移：[分组模型倍率：绝对值 → 系数](group-model-ratio-coefficient.md)。

## 问题

语义迁移的执行者是**新版本的进程**：它启动、连上库、把旧值换算成新值写回去，然后开始服务。
这套流程隐含一个假设——**换算完成的那一刻起，读这份数据的只有新版本**。

蓝绿部署和滚动更新都会打破这个假设。它们为了不中断服务，会先把新容器拉起来、等它健康，
再把流量切过去、最后才移除旧容器。于是出现一段两个版本并存的窗口：

```
t0  新容器启动，执行迁移，库里的值改写为新语义
        ↓  ← 危险窗口：旧容器还在跑，还在按旧语义读这份数据
t1  流量切到新容器
t2  旧容器被移除
```

`t0` 到 `t2` 之间，旧容器读到的是新语义的值，但它按旧语义解释。以分组模型倍率为例：
迁移把 `zheng/claude-fable-5` 从 `4`（绝对倍率）换算成 `0.8`（系数），
旧版本会把 `0.8` 读成「最终倍率 0.8」，而正确价格是 `5 × 0.8 = 4`——**少收 5 倍**。

这与迁移手册里「多节点必须主节点先行」是**同一个风险**，只是换了副面孔：
那里是两台机器同时在跑，这里是同一台机器上的两个容器同时在跑。

## 窗口有多长

取决于两件事，两者取较长的一个：

- **部署编排的重叠时间**：从新容器通过健康检查到旧容器被移除，通常几十秒到几分钟。
- **旧容器的选项同步周期**：从节点/进程通过定时同步刷新内存里的选项，默认 **60 秒**。
  旧容器不是立刻看到新值的——它在下一次同步之前仍然用着内存里的旧值，反而是安全的。

所以实际暴露时间约等于「重叠时间 − 60 秒」，重叠很短时可能是零。
但这只是概率上的安慰，不是保证：Redis 缓存失效、进程重启、请求触发的读路径都可能提前拿到新值。

## 怎么办

按代价从低到高，任选其一：

### 1. 确认这段窗口没有相关流量（最省事，适合小范围配置）

语义迁移影响的往往只是一小部分数据——某个分组、某几个模型。
如果这部分在部署窗口里根本没有流量，风险就是零。

2026-08-26 生产升级就是这种情况：受影响的只有 `zheng` 分组，而该分组当时没有任何用户、
全时段消费记录为 0，所以两分钟的重叠窗口不构成任何影响。

事后核查的方法（以分组模型倍率为例）：

```bash
# 迁移时间点从新容器日志里取
ssh <host> 'docker logs <新容器> 2>&1 | grep "已迁移为系数语义"'

# 查该时间点之后、旧容器移除之前，受影响分组有没有消费记录
curl -sS "$BASE/api/log/?p=0&page_size=100&group=<受影响分组>&start_timestamp=<迁移时刻>" \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "New-API-User: 1"
```

有记录就逐条核对 `other` 里的 `group_ratio`：等于新系数说明是新容器处理的（正常），
等于旧的绝对值说明是旧容器处理的（错误计费，需要人工补差）。

### 2. 停机部署（最稳，适合影响面大的迁移）

先停旧容器、再起新容器，牺牲几十秒可用性换取零重叠。
受影响的分组/模型有实际流量、或者换算倍数很大时，用这个。

### 3. 让部署编排先摘流量再启动新版本

如果编排工具支持「先把旧实例从负载均衡摘掉、再拉新实例」，效果等同于停机部署但对外更平滑。

## 给自动化助手的判定

执行语义迁移类升级时，在部署**之前**回答这三个问题：

1. 这次升级是否改变了已有数据的含义？（看 release note / 迁移手册；不改含义的升级不适用本文）
2. 部署方式是否会让新旧版本并存？`docker ps` 在部署后立刻看一眼，同时存在两个同名服务容器即是。
3. 受影响的数据范围（哪些分组、哪些模型）在窗口期是否有流量？

第 1 题为否 → 正常部署。第 1 题为是、第 2 题为否 → 正常部署。
第 1、2 题都为是 → 按第 3 题的结论选停机部署（有流量）或事后核查（无流量）。

**不要**在窗口期用「反正只有一两分钟」搪塞过去而不做任何核查——计费错误不会自己暴露，
它只会变成账单上一个没人注意到的数字。
