# 分组模型倍率配置说明

面向管理员。这份文档说明如何给某个分组下的某个模型单独定价，而不影响该分组的其他模型，也不影响其他分组。

终端用户看的文档是 [group-pricing.md](../user/group-pricing.md)。设计文档是 [group-model-ratio.md](../../specifications/group-model-ratio.md)。

## 这个功能解决什么

系统原有的分组定价只有一个粗粒度旋钮：**分组倍率**，它对该分组的所有模型统一打折。
「vip 分组整体八折」能做，「vip 分组的 gpt-4o 单独打五折、其他模型不变」做不了。

以前的绕法是克隆一个改名模型（`gpt-4o-vip`）再用渠道重定向指回去。代价是模型列表被污染、
用户看到语义不明的名字、每加一个特价就多一个假模型。

**分组模型倍率**给出第二个维度：按「分组 × 模型」定倍率。

## 一条必须先记住的规则

> **分组模型倍率就是这个模型在这个分组的分组倍率。**

它**取代**分组倍率，不和分组倍率叠加；模型自己的定价方式不变——按量倍率模型照常乘全局模型倍率，
固定价模型照常乘固定价，阶梯计费模型照常按表达式算。所以你配的时候不需要关心这个模型是哪种计费方式。

说得再准确一点：计价时「分组倍率」只有**一个**槽位，三个来源按优先级取**一个**，彼此不相乘：

```
分组倍率 = 分组模型倍率[计费组][模型]      ← 配了就用它，下面两个都不看
        或 分组间覆盖[用户组][计费组]       ← 没配分组模型倍率、但配了分组间覆盖
        或 分组比率[计费组]                ← 都没配

最终价 = 模型自身的价格 × 分组倍率
```

所以 `全局倍率 × 分组倍率 × 分组模型倍率` 这种三连乘**不存在**。
被取代的也不只是分组比率——`分组间覆盖`（`GroupGroupRatio`）同样失效，
否则它会从另一条路把折扣叠回来。

举例：全局 `gpt-4o` 倍率 10，vip 分组倍率 0.8。

| 配置 | vip 用 gpt-4o 的最终倍率 |
|---|---|
| 不配 | 10 × 0.8 = **8** |
| 分组模型倍率 = 0.5 | 10 × 0.5 = **5**（不是 10 × 0.8 × 0.5 = 4） |

填的是**折扣系数**，不是绝对价。想让 vip 的 gpt-4o 打五折就填 0.5；想让它比原价还贵就填大于 1 的值。

vip 的其他模型仍然享受 0.8 的分组倍率，只有配了的那个模型改用自己的系数。

**前提：模型必须先有价格。** 分组模型倍率只替换分组倍率，不给模型定价。
一个既没有全局模型倍率、也没有固定价或计费表达式的模型，光配分组模型倍率是用不了的，
它既不会出现在 `/v1/models` 里，也无法计费。请先配好模型自己的价格，再来配分组差异。

## 配置步骤

### 1. 进入配置页

**系统设置 → 模型相关设置 → 分组比例（Group ratios）**，点右上角**切换到 JSON**。

分组模型倍率目前只能在 JSON 模式下编辑，可视化编辑器暂无入口。

### 2. 填写 `分组模型倍率`

嵌套 JSON，外层是分组名，内层是模型名到倍率：

```json
{
  "vip": {
    "gpt-4o": 0.5,
    "claude-3-5-sonnet": 0.6
  },
  "svip": {
    "gpt-4o": 0.3
  }
}
```

含义：vip 分组用 `gpt-4o` 按全局倍率的 0.5 倍计费，`claude-3-5-sonnet` 按 0.6 倍；
svip 的 `gpt-4o` 按 0.3 倍。两个分组里没列出的模型，照常按 `全局模型倍率 × 分组倍率` 计算。

### 3. 保存

点**保存分组比率**。倍率必须 ≥ 0，负数会被拒绝。

如果这个配置是给内部分组、专属分组用的，保存之后还要确认这个分组是不公开的——分组默认并不是私有的，见[让分组不公开](#让分组不公开)。

## 生效范围

三种计费方式都生效，规则完全一样：填 0.8 就是这个模型在这个分组打八折。

| 模型的计费方式 | 效果 |
|---|---|
| 按量倍率 | `全局模型倍率 × 该值` |
| 固定价（在「模型固定价格」里配了价的） | `固定价 × 该值` |
| 表达式计费（`tiered_expr`） | `表达式算出的价格 × 该值`，阶梯结构不变 |

阶梯模型的长上下文加价关系不受影响，整张价目表按比例平移。
固定价模型的按次价格整体乘系数，图片张数、时长这类倍率照常在上面相乘。

## 派生价格怎么变

系数作用在**整体价位**上，其他倍率照常在它上面相乘：

```
输入价 = 全局倍率 × 系数
输出价 = 全局倍率 × 系数 × 补全倍率
缓存价 = 全局倍率 × 系数 × 缓存倍率
按次价 = 固定价 × 系数 × （张数、时长等倍率）
```

这几个式子里**没有分组倍率不是漏写**——系数已经占了分组倍率那个槽位。

所以它调整的是这个模型在这个分组的整体价位，各项之间的比价关系不变。
如果需要单独调输出价，当前版本做不到。

## 几个常用配法

### 给某个分组的旗舰模型做特价

```json
{ "vip": { "gpt-4o": 0.5 } }
```

### 让某个分组免费用某个模型

倍率填 0，会走系统既有的免费模型逻辑（不预扣、不计费）：

```json
{ "internal": { "gpt-4o-mini": 0 } }
```

这种配法通常配合不公开的分组使用，否则所有人都能白嫖，见[让分组不公开](#让分组不公开)。

### 给某个分组的某个模型加价

系数大于 1 就是加价，用来给昂贵模型在低价分组里回收成本：

```json
{ "cheap": { "gpt-4o": 2 } }
```

### 给按次计费的绘图 / 视频模型做分组差异化

写法一样，系数乘在固定价上：

```json
{ "vip": { "gpt-image-1": 0.5 } }
```

### 分组之间互不影响

```json
{
  "vip":  { "gpt-4o": 0.5 },
  "svip": { "gpt-4o": 0.3 }
}
```

`default` 分组没列出来，它的 `gpt-4o` 仍按 `全局倍率 × default 分组倍率` 算。

### 给阶梯计费模型做分组差异化

和按量模型写法完全一样：

```json
{ "vip": { "claude-sonnet-4-5": 0.8 } }
```

vip 用这个模型时，表达式算出的价格（含长上下文分档）整体打八折。
如果要给某个分组一张**结构不同的阶梯价目表**（不只是整体打折），当前版本做不到。

## 从旧版本升级

> 实际升级操作请按 [guides/migration/group-model-ratio-coefficient.md](../migration/group-model-ratio-coefficient.md)
> 走一遍：那份是操作手册，含备份、日志核对、验证、失败处理和回滚。本节只解释语义变化。

早期版本的分组模型倍率是**绝对值**语义：填 5 表示「该分组下这个模型的最终倍率就是 5」。
现在改成了系数。升级后首次启动时（仅主节点）会自动换算已有配置：

```
新值 = 旧值 ÷ 该模型的全局模型倍率
```

换算与分组倍率无关——旧语义下分组倍率对配了值的模型本来就不生效，所以价格保持不变。
换算只做一次，靠 `GroupModelRatioSemantics` 选项标记，重启不会重复换算。

**两类条目会被移除**，都会在后台日志里逐条列出，格式 `分组/模型=原倍率`：

1. **模型没有配全局模型倍率**（旧语义允许只配分组值就能计费，新语义不允许），或全局倍率为 0。
   这类条目在新语义下无法表达原来的价格，保留会按错误的价格计费。

   > 分组模型倍率迁移：以下条目没有对应的全局模型倍率，无法换算成系数，已被移除，请重新配置……

2. **配在固定价模型上的条目**。旧版本里它们本来就不生效（静默失效），而新版本对固定价模型
   同样生效——如果原样换算，这些分组的价格会在升级后突然变化。

   > 分组模型倍率迁移：以下条目配在固定价模型上，旧版本中本来就不生效，已被移除……

升级后请检查一次启动日志。第一类先给模型配好全局模型倍率再重配系数；
第二类如果确实想给固定价模型打折，现在可以直接按系数配上。

### 升级前先备份这一项

迁移后库里存的是系数。如果之后要回滚到旧版本，旧版本会把 `0.5` 读成「最终倍率 0.5」，
**少收到 1/10**。所以回滚必须连数据一起回滚，而这需要迁移前的原始值：

```sql
-- 升级前备份（PostgreSQL 用 "key"，MySQL / SQLite 用 `key`）
SELECT value FROM options WHERE "key" = 'GroupModelRatio';

-- 回滚时恢复
UPDATE options SET value = '<备份出来的 JSON>' WHERE "key" = 'GroupModelRatio';
DELETE FROM options WHERE "key" = 'GroupModelRatioSemantics';
```

### 多节点部署要主节点先行

迁移只在主节点（`NODE_TYPE` 不是 `slave`）执行，从节点靠选项同步（默认 60 秒）拿结果。
从节点是按**新语义**解释库里的值的，所以如果从节点先升级、主节点还没迁移完，
这段时间它会把旧的绝对倍率当成系数，超收一个数量级。

顺序：全部停 → 只起主节点 → 确认日志里有那条迁移成功 → 再起从节点。

### 迁移失败会导致启动失败

有存量配置且迁移出错时进程会直接退出（日志里是 `[FATAL] ... migration left an unsafe state`），
这是故意的：这种状态下继续服务会按错的价格计费。处理办法是修好数据库连接/权限后重启，
迁移会重新尝试。没有存量配置时不会阻断启动。

## 让分组不公开

**在 `分组比率` 里配了一个分组，不等于这个分组只有你知道。** 分组对谁可见由同一个配置页上的另一张白名单决定：**用户可用分组**（`UserUsableGroups`）。列在这张表里的分组是完全公开的——任何人都能在定价页看到它的倍率（包括未登录的访客），也能在令牌里选中它来用。

这一点对分组模型倍率尤其重要：给某个分组配了内部特价，却把这个分组留在「用户可用分组」里，等于把特价公开挂牌卖。

### 完全私有：只有属于该分组的用户能看见

1. 在 `分组比率` 里给这个分组配一个倍率（**必须配**，见下文）。
2. **不要**把它写进 `用户可用分组`。
3. 在用户管理里，把需要享受这个价格的用户的「分组」直接改成这个分组。

系统会自动把用户自己所属的分组算作可用分组，所以这批用户能正常调用、能在定价页看到打折后的价格；其他用户完全看不到这个分组的存在，也无法在令牌里选中它。

例：`internal` 分组的 `gpt-4o` 按两折计费，只有被划入 `internal` 的用户可见。

```json
// 分组比率 GroupRatio —— 必须有条目
{ "default": 1, "internal": 1 }

// 用户可用分组 UserUsableGroups —— 故意不写 internal
{ "default": "默认分组" }

// 分组模型倍率 GroupModelRatio
{ "internal": { "gpt-4o": 0.2 } }
```

### 定向开放给某几个用户分组

想让「vip 用户也能用这个私有分组」，用 **分组特殊可用分组**（`GroupSpecialUsableGroup`）。外层键是**用户所属的分组**，内层键是要增减的分组，值是展示用的描述：

```json
{ "vip": { "+:internal": "内部特价" } }
```

`+:` 表示追加，`-:` 表示反向屏蔽（把一个公开分组对某个用户分组隐藏），不带前缀等同于追加。这条规则只对 `vip` 用户生效，其他分组的用户不受影响。

### 私有分组仍然要有分组比率

不公开的分组同样必须在 `分组比率` 里有条目。缺条目会导致这个分组无法被令牌选中、也进不了 auto 分组，后台日志还会反复出现 `group ratio not found`。

反过来，`分组比率` 里有条目不代表公开——公开性只看 `用户可用分组`。

### 不公开之后的实际表现

| 位置 | 属于该分组的用户 | 其他用户 |
|---|---|---|
| 模型广场 / 定价接口 | 能看到该分组的分组倍率与分组模型倍率 | 分组本身、分组倍率、分组模型倍率全部不下发 |
| 令牌的分组下拉 | 可选 | 不出现 |
| 令牌指定该分组发请求 | 正常 | 被拒绝 |

## 验证配置

### 看定价页

用属于该分组的账号打开模型广场，找到这个模型，看展示价是否等于 `原价 × 系数`。
定价页的分组筛选切到具体分组，看到的就是那个分组的价格。

不筛选分组时，模型卡片显示的是该用户**所有可用分组里的最低价**，分组模型倍率会参与这个比较。

### 看账单

发一条请求，然后在日志详情里看倍率：

- `model_ratio` 应等于**全局**模型倍率（不是你配的值）
- `group_ratio` 应等于你配的分组模型倍率

如果 `group_ratio` 还是该分组原本的分组倍率，说明没命中——检查分组名和模型名是否写对。
固定价模型看「模型价格 + 分组倍率」，阶梯计费模型没有 `model_ratio`，都只看 `group_ratio`。

## 排障

**配了没反应**

按顺序查：

1. 这个模型有全局价吗？只配分组系数、没配全局模型倍率（或固定价、表达式）是不行的。
2. 分组名写对了吗？要写**计费分组**，不是用户分组。用户属于 A 组但令牌指定了 B 组时，
   计费用的是 B 组。
3. 模型名写对了吗？要写系统里的模型名，注意有些模型会做名称归一（比如思考预算变体）。
4. 是不是异步任务模型？提交时预扣、终态时结算，看最终结算后的额度。
5. 升级过来的？看一次启动日志，这个条目可能在迁移时被移除了。

**账单比预期贵很多**

最常见的原因是把系数当成了绝对倍率。填 5 不是「最终倍率 5」，而是「原价的 5 倍」。
想要五折填 0.5。升级过来的站点如果看到某个模型突然贵了几个数量级，检查一下这个字段。

**用了 auto 分组的请求，账单对不上**

auto 分组会在重试时切换计费分组，系数跟着最终落地的那个分组重新解析。
账单里的分组以日志中的实际分组为准，不一定是令牌上写的第一个分组。

**不想让所有人看到这个特价**

分组默认是公开的，把它从 `用户可用分组` 里去掉才是私有分组，见[让分组不公开](#让分组不公开)。

**改了配置多久生效**

立即生效，走的是和其他倍率配置一样的热更新通道，不需要重启。

## 与其他分组配置的关系

| 配置 | 作用 | 与分组模型倍率的关系 |
|---|---|---|
| 模型倍率（`ModelRatio`） | 按量模型的全局价 | 前提条件，系数乘在它上面 |
| 模型固定价格（`ModelPrice`） | 按次计费价 | 前提条件，系数乘在它上面 |
| 分组比率（`GroupRatio`） | 分组统一折扣 | 命中时对该模型被取代；私有分组也必须在这里有条目 |
| 分组间覆盖（`GroupGroupRatio`） | A 组用户按 B 组计费时的折扣 | 命中时对该模型被取代 |
| 用户可用分组（`UserUsableGroups`） | 决定分组对谁可见、可选 | 不影响计费，但决定谁能看到折后价 |
| 分组特殊可用分组（`GroupSpecialUsableGroup`） | 按用户分组增减可用分组 | 同上，用于把私有分组定向开放 |
| 充值分组比率（`TopupGroupRatio`） | 充值定价 | 无关，不受影响 |
