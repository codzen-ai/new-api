# 用量对账单导出使用说明

面向运营人员。这份文档说明如何导出用量对账单，以及表格里每一列的含义。

## 这份表是什么

对账单是**给客户看的账单明细**，一行对应一次 API 调用。它的设计目标只有一个：**客户拿到表格后，能自己算清楚每一笔钱是怎么来的**。

因此表里只保留客户需要核对的信息，不包含渠道名称、上游供应商、客户请求内容、客户 IP 这些内容——前两者是我们的供应商结构，后两者是客户自己的数据，都不应该出现在账单上。

## 怎么导出

1. 进入 **用量日志** 页面
2. **把「类型」筛选成「消费」** —— 这一步很重要，见下方注意事项
3. 设置时间范围，以及需要的其他筛选条件（用户、令牌、模型、分组等）
4. 点击工具栏的下载图标导出

导出的文件名形如 `statement_20260802_143000.csv`。

几个限制：

- 只有**管理员**能导出
- 单次最多 **10 万行**，超出会提示「记录数量超出限制，请缩小查询范围」，此时缩短时间范围分批导出即可
- 导出结果与页面上筛选出的内容一致，包括列筛选。**唯一的例外是退款行**：类型选「消费」时，导出会额外带上同条件下的退款记录（页面上看不到它们）。这是刻意的——视频等异步任务的费用由「消费 + 退款」两条记录净额构成，只导消费会严重高估，详见[「视频等异步任务：一笔费用两行」](#视频等异步任务一笔费用两行)

## 列说明

表格共 26 列。

### 标识信息

| 列名 | 含义 | 记录 C 的值 |
|---|---|---|
| `time` | 调用发生时间，**东八区（UTC+8）**，格式 `2026-08-02 14:30:00` | `2026-07-23 15:21:07` |
| `request_id` | 请求唯一编号。客户对某一笔有疑问时，让他提供这个编号，我们可以精确定位到那次调用 | `...GPu9tMvl` |
| `username` | 用户名 | `dd4357` |
| `token_name` | 使用的令牌名称。客户通常按令牌区分不同业务/项目，这一列用来分摊成本 | `张` |
| `model` | 调用的模型名称 | `claude-opus-4-8` |
| `task_id` | 异步任务编号，只有视频生成、绘图这类异步任务才有；同一个任务的多行用它归组 | 空 |

同步调用的费用只占一行，`task_id` 为空。异步任务的两行 `request_id` 与 `task_id` 都相同（示例 E、F）。

### 计费方式

| 列名 | 含义 | 记录 D 的值 |
|---|---|---|
| `entry_type` | 这一行在整笔费用里是什么，四种取值见下表 | `consume` |
| `billing_mode` | `per_token` = 按 token 计费；`per_call` = 按次计费 | `per_token` |
| `tier` | 分级计费时命中的档位名；非分级计费的模型为空 | `long_context` |

`entry_type` 的四种取值：

| 取值 | 含义 | 金额符号 |
|---|---|---|
| `consume` | 一次调用的完整费用，看这一行就够了 | 正 |
| `prepaid_hold` | 异步任务**提交时的预扣占位**，不是最终扣费（示例 E） | 正 |
| `settlement` | 异步任务的**补扣**：实际用量高于预扣，补收差额 | 正 |
| `refund` | **退还**：异步任务实际用量低于预扣，或任务失败全额退回（示例 F） | **负** |

**按次计费**（如部分绘图模型）不按 token 算钱，所以这一行的 token 数、单价、分项金额全部为空，费用整笔计入 `other_amount`。这是正常的，不是数据缺失。

**分级计费**（按上下文长度等条件切换档位的模型，示例中的 B、D、C 都属于这一类）仍然是按 token 计费，`billing_mode` 显示 `per_token`，各项单价和金额照常拆出来，客户验算方式没有区别。这类模型**不同档位的单价不同**，`tier` 列写的就是这次调用命中了哪一档。

对照 B 和 D——同一个模型 `gpt-5.5`，B 的 `tier` 是 `standard`、输入单价 35，D 的 `tier` 是 `long_context`、输入单价 70。D 的输入是 24 万 token，超过了 20 万的分档阈值，整笔按高价档计费。这不是计费错误，是该模型本身的价目表如此。

**`tier` 为空 = 这个模型不分档**（记录 A 就是），单价固定，不会出现同模型不同价的情况。客户拿两行质疑单价不一致时，先看 `tier` 列：档位不同就是跨档，档位相同还不一致才需要我们排查。

极少数情况下系统无法确认某一行的拆分是否准确（例如定价规则依赖了账单里不保留的请求信息），这时会**留空各项明细、把整笔费用放进 `other_amount`**，而不是给出一个可能不对的单价。这类行仍然满足各项之和等于 `total_amount`。

### 输入

| 列名 | 含义 | 记录 B 的值 |
|---|---|---|
| `input_tokens` | **按输入单价实际计费的 token 数** | `1725` |
| `input_price_per_1m` | 输入单价，每 100 万 token 的金额 | `35.000000` |
| `input_amount` | 输入费用 = `input_tokens ÷ 1,000,000 × input_price_per_1m` | `0.060375` |

记录 B 验算：`1725 ÷ 1,000,000 × 35 = 0.060375` ✅

这次调用上游返回的 prompt 一共 99389 token，其中 97664 命中缓存、按缓存价单独收费，所以真正按输入价收钱的只有 1725。

> ⚠️ **`input_tokens` 不等于上游账单上的 prompt tokens。**
>
> 不同厂商统计口径不一样：OpenAI 把缓存命中的 token 算在 prompt tokens 里，Anthropic 则单独列出。如果直接照搬原始数字，这一列的含义会**逐行变化**，客户根本没法求和。
>
> 所以这一列统一成「真正按输入单价收费的那部分 token」，已经扣除了缓存读、缓存写、图片、音频等按其他单价计费的部分。客户想核对总输入量时，应该把 `input_tokens + cache_read_tokens + cache_write_tokens` 加起来看。

### 缓存读（cache read）

命中缓存的部分，单价远低于普通输入，这是给客户省钱的地方。

| 列名 | 含义 | 记录 B 的值 |
|---|---|---|
| `cache_read_tokens` | 命中缓存的 token 数 | `97664` |
| `cache_read_price_per_1m` | 缓存读单价，每 100 万 token | `3.500000` |
| `cache_read_amount` | 缓存读费用 | `0.341824` |

记录 B 验算：`97664 ÷ 1,000,000 × 3.5 = 0.341824` ✅

缓存读单价 3.5 是输入单价 35 的十分之一。这行 97664 个 token 如果按输入价收，要 3.42 元，走缓存只花了 0.34 元——客户问「缓存到底省了多少」，就这么算给他看。

记录 C 的三个 `cache_read_*` 列是空的：那次调用全是新建缓存，没有命中。

### 缓存写（cache write）

建立缓存的部分，单价通常**高于**普通输入（一次性投入，后续读取才便宜）。

| 列名 | 含义 | 记录 C 的值 |
|---|---|---|
| `cache_write_tokens` | 写入缓存的 token 数 | `83917` |
| `cache_write_price_per_1m` | 缓存写单价，每 100 万 token | `43.750000` |
| `cache_write_amount` | 缓存写费用 | `3.671369` |

记录 C 验算：`83917 ÷ 1,000,000 × 43.75 = 3.671369` ✅ ——占了这一行 3.849594 的绝大部分。

同一个模型，缓存写 43.75 比普通输入 35 贵，而缓存读只要 3.5。所以**缓存写是一次性投入，后续命中得够多就回本了**。客户看到某一行特别贵，通常就是这种建缓存的调用，紧接着的几行会明显便宜下来——记录 C 之后的同一批调用就是这个走势。

> Claude 的缓存分 5 分钟和 1 小时两种有效期，单价不同。当一次调用同时用了两种时，`cache_write_price_per_1m` 显示的是**按实际用量加权后的混合单价**。金额仍然是精确的，用这个单价乘 token 数也能对上。

### 输出

| 列名 | 含义 | 记录 B 的值 |
|---|---|---|
| `output_tokens` | 模型生成的 token 数 | `288` |
| `output_price_per_1m` | 输出单价，每 100 万 token | `210.000000` |
| `output_amount` | 输出费用 | `0.060480` |

记录 B 验算：`288 ÷ 1,000,000 × 210 = 0.060480` ✅

输出单价通常是输入的好几倍（B 是 6 倍，A 是 8 倍），所以一次调用哪怕只生成几百个 token，费用也可能和几千个输入 token 相当。

### 金额汇总

| 列名 | 含义 | 记录 B 的值 |
|---|---|---|
| `other_amount` | 上述四项之外的所有费用 | `0.000007` |
| `calculation` | 这一行的完整算式 | `1725×35.000000÷1M + 97664×3.500000÷1M + 288×210.000000÷1M + 0.000007 = 0.462686` |
| `total_amount` | **本次调用实际扣费金额**，与系统扣的钱完全一致 | `0.462686` |
| `currency` | 币种，跟随站点设置（当前为 `CNY`） | `CNY` |
| `exchange_rate` | 本次导出使用的美元汇率 | `7` |

**`calculation` 是给客户直接看的**：不用翻文档、不用自己搭公式，一眼就知道这笔钱怎么算出来的。里面每一个数字都能在同一行的其他列里找到，`÷1M` 表示单价是按每 100 万 token 计的。末尾那个不带 `×` 的数（示例中的 `+ 0.000007`）就是 `other_amount`；它小到显示为 0.000000 时会省略，为负数时写成 `- 0.00000x`。

按次计费、以及无法拆分的行，这一列是空的——那种行没有算式可讲，`total_amount` 就是全部。

> 这一列是**纯文本**，不是 Excel 公式。账单是一份已经发生的记录，不应该在客户排序、筛选或误改某一格之后自己变一个数出来。要让 Excel 真的替你算，在空列里粘 `=J2/1000000*K2+M2/1000000*N2+P2/1000000*Q2+S2/1000000*T2+V2`（依次是输入、缓存读、缓存写、输出、其他五项），再和 X 列 `total_amount` 比对即可。

**`other_amount` 里装的是什么：**

- 按次计费模型的整笔费用
- 图片、音频等按独立单价计费的部分
- 工具调用（如联网搜索）的附加费
- 结算时的小数舍入差额（通常是 0.000001 量级）
- 无法确认拆分准确性的分级计费行的整笔费用（见上方「计费方式」）

这一列是用 `total_amount` **减去**前面四项算出来的，不是把各种杂费加起来。这样设计是为了保证：**无论产生了什么费用，各项之和永远等于实际扣款**，不会出现账单里少了一笔钱却看不出来的情况。

## 视频等异步任务：一笔费用两行

视频生成这类任务是异步的：提交时还不知道会用掉多少 token，系统先扣一个占位额度，等上游把视频生成完、返回真实用量之后（通常三到四分钟）再结算差额。**所以一次视频生成在账单里通常是两行**，`task_id` 相同：

| `entry_type` | 这一行是什么 | 示例 E / F |
|---|---|---|
| `prepaid_hold` | 提交时的预扣占位，**不是最终扣费** | `10.500000` |
| `refund` 或 `settlement` | 结算：多扣的退回（负数）／少扣的补收（正数） | `-8.373204` |

净额才是这次视频真正的花费：`10.500000 − 8.373204 = 2.126796`。

三点必须清楚：

- **只看 `prepaid_hold` 会严重高估**。示例这一笔预扣 10.5 元、实收 2.13 元，是 4.9 倍。所以类型选「消费」导出时，退款行会被一并带出来，**不要手工删掉负数行**。
- **结算行的明细读法和普通行不同**。`output_tokens` 是上游认定的计费用量，`output_amount` 是**这次任务最终应收的全额**，`other_amount` 则是**冲回的预扣占位**（负数）。所以 F 行的算式是 `100858×21.087033÷1M - 10.500000 = -8.373204`：先算实际该收多少，再把预扣的减掉，剩下的就是这一行的金额。
- **任务失败时只有一行退款**，金额等于预扣额度、方向为负，与提交那行相抵为零 —— 失败不收费。这类行没有 `output_tokens`，因为它没有产生任何用量。

跨账期的情况：提交和结算可能落在不同的日期，甚至跨月（22:13 提交、次日 00:05 结算）。这种任务的两行会出现在**两份账单里**，各自都是按发生时间归期的。对账时以结算行落在哪一期为准，或者把账期边界前后一小时的 `task_id` 单独核一遍。

如果一个 `prepaid_hold` 行在同一 `task_id` 下**找不到结算行**，说明上游没有返回用量，预扣额度就是最终扣费。这种情况本身值得排查（上游用量缺失），但账单金额是对的。

### 在 Excel 里按任务归组

按 `task_id` 排序后，同一个任务的行会挨在一起，用 `SUMIF` 就能得到每个任务的实收金额：

```
=SUMIF(F:F, F2, X:X)     // F 列是 task_id，X 列是 total_amount
```

`task_id` 为空的行（普通同步调用）本身就是完整的一笔，不需要归组。

## 怎么验算

对账单的 `calculation` 列已经把每一行的算式写好了，下面是它背后的规则。

每一行都满足（误差不超过 0.000001，原因见下）：

```
input_amount + cache_read_amount + cache_write_amount + output_amount + other_amount = total_amount
```

退款行同样满足，只是 `total_amount` 与部分分项为负数。整期总额直接对 `total_amount` 求和即可 —— **负数行会自动抵扣，不需要区别对待**。

六条示例记录代进去：

```
              输入      缓存读     缓存写      输出        其他         合计       total_amount
A:  0.013757 + 0.132026 +        0 + 0.126518 +  0.000000 =  0.272301    0.272300  差 0.000001
B:  0.060375 + 0.341824 +        0 + 0.060480 +  0.000007 =  0.462686    0.462686  ✅
D: 16.800000 +        0 +        0 + 0.504000 +  0.000000 = 17.304000   17.304000  ✅
C:  0.000070 +        0 + 3.671369 + 0.178150 +  0.000005 =  3.849594    3.849594  ✅
E:         0 +        0 +        0 +        0 + 10.500000 = 10.500000   10.500000  ✅
F:         0 +        0 +        0 + 2.126796 −10.500000  = −8.373204   −8.373204  ✅
```

验算时**空格按 0 计算**（A、B、D 没有缓存写，C、D 没有缓存读，E 没有任何明细）。

> A 行差了 0.000001，这不是账错了。表格里每一格都四舍五入到 6 位小数，A 行 `other_amount` 的真实值是 −0.00000035，显示成了 0.000000。**逐行验算允许 ±0.000001 的偏差**，整期求和时这种偏差会互相抵消，不影响总额。

前四行的 `other_amount` 都是 0.00000x 量级，这是正常的：**它只是结算取整留下的零头**。如果某一行的 `other_amount` 明显偏大，说明这次调用有 token 之外的费用（图片、音频、联网搜索等），或者是按次计费的行、异步任务的预扣与结算行（E、F 那两种）。

单项金额也可以自己算：

```
分项金额 = 该项 token 数 ÷ 1,000,000 × 该项单价
```

在 Excel 里加一列验算公式即可批量核对，判断条件用 `ABS(各项之和 - total_amount) <= 0.000001`。整期总额把 `total_amount` 求和。

## 常见问题

**Q：某些格子是空的，是不是数据丢了？**

不是。空格表示「这次调用没有这类费用」或「这项在本行不适用」，例如没有命中缓存时，三个 `cache_read_*` 列就是空的。空格和 0 的含义不同：0 表示确实测量到了但金额为零，空表示这项不适用。

如果**一整行的四组明细都是空的**，只有 `total_amount` 和 `other_amount` 有值，说明这一行是按次计费、异步任务的预扣占位（`entry_type` = `prepaid_hold`），或者是系统无法确认拆分准确性的分级计费行。金额本身没有问题，客户对这类行有疑问时把 `request_id` 给我们即可查明细。

**Q：为什么有负数金额的行？**

那是退款行（`entry_type` = `refund`），异步任务预扣多了退回、或者任务失败全额退回。它和同一个 `task_id` 的预扣行相抵才是实际扣费，**不要删掉**。详见[「视频等异步任务：一笔费用两行」](#视频等异步任务一笔费用两行)。

**Q：为什么导出来有一堆不是消费的记录？**

导出会跟随页面上的「类型」筛选。如果类型选的是「全部」，充值、管理操作、错误日志、登录记录都会一起导出。**对账前务必把类型选成「消费」。**

类型选「消费」时，导出会**额外**带上退款记录（页面上看不到），这是刻意的：不带上它们，视频等异步任务就会按预扣占位收费。除退款之外不会混进任何其他类型。

**Q：同一个时间段，这个月导和上个月导，人民币金额不一样？**

金额按导出时的系统汇率换算。如果中途调整过汇率，历史数据的人民币金额会随之变化（美元口径不变）。`exchange_rate` 列记录了本次导出用的汇率，出现争议时以客户手上那份账单的这一列为准。

**如果需要金额长期稳定，建议对账单一经发出就归档保存原始文件**，而不是每次重新导出。

**Q：单价和模型价目表对不上？**

单价是**该次调用实际生效的价格**，包含了分组倍率等因素。不同分组的客户单价本来就不同。另外单价快照的是**调用发生时**的价格，之后调整模型倍率不会改变历史账单——这是刻意设计的，保证已发出的账单不会变。

**Q：同一个模型，为什么这一行单价 35，那一行单价 70？**

看 `tier` 列。分级定价的模型按上下文长度切档，超过阈值的请求整笔走高价档，`tier` 写的就是命中的档位名（示例中 B 是 `standard`、D 是 `long_context`）。两行档位不同就是跨了档，对比 token 总量（`input + cache_read + cache_write`）能印证。

如果两行 `tier` 相同而单价不同，那才需要找我们排查。

**Q：`total_amount` 和客户在网页上看到的消费金额一致吗？**

一致。两者用同一套汇率和币种设置，来源都是系统实际扣费记录。

注意页面上的「消费额度」统计只累加消费记录、不减退款，所以有视频任务时**页面统计会高于账单求和**。以账单为准。

**Q：Excel 打开中文乱码？**

不会。文件带 UTF-8 BOM，Excel 能正确识别。如果用其他工具打开出现乱码，指定 UTF-8 编码即可。
